# MGRQ-Net I23｜组件级匈牙利匹配器报告

## 1. 执行结论

I23 已完成并通过验收（`PASSED`）。本阶段实现了查询与GT组件之间的一对一匈牙利匹配，并为所有未匹配查询返回明确的`-1`无目标标记。

第一版匹配代价严格采用：

\[
C_{ij}=2L_{Dice}+2L_{BCE}+L_{box}
\]

其中`L_box`为归一化`xyxy`坐标上的平均L1距离。第一版不加入语义代价，避免DeepSeek弱语义直接改变组件监督分配。

## 2. 输入与输出协议

### 2.1 输入

| 输入 | 形状 | 说明 |
|---|---|---|
| 查询掩码logits | `[B,Q,H,W]` | 解码器对每个查询预测的组件掩码 |
| 查询框 | `[B,Q,4]` | 归一化`xyxy`坐标，范围`[0,1]` |
| GT组件掩码 | `[B,G,H,W]` | 来自I20组件目标 |
| GT组件框 | `[B,G,4]` | I20像素框除以图像宽高得到 |
| 查询有效位 | `[B,Q]` | 排除批内padding槽 |
| GT有效位 | `[B,G]` | 排除批内padding组件 |

### 2.2 输出

每张图返回：

- 已匹配查询索引；
- 已匹配GT组件索引；
- `target_for_query`：长度为Q，匹配项保存GT索引，未匹配项为`-1`；
- 未匹配查询索引；
- 未匹配GT索引；
- 每个有效匹配的总代价。

匹配过程在`torch.no_grad()`中执行。匈牙利分配本身不参与反向传播，后续损失应根据匹配索引在原预测张量上重新计算。

## 3. 三项代价的具体定义

### 3.1 Soft Dice代价

对查询概率图与二值组件掩码计算成对soft Dice损失，平滑项为1：

\[
L_{Dice}=1-\frac{2\sum p g+1}{\sum p+\sum g+1}
\]

### 3.2 BCE代价

使用逐像素`BCEWithLogits`的空间均值。实现通过矩阵乘法直接计算`Q×G`代价矩阵，不创建`Q×G×H×W`中间张量，从而减少多组件图上的显存占用。测试已与PyTorch直接BCE结果逐项核对。

### 3.3 框代价

查询框和GT框均采用`[0,1]`范围的`xyxy`格式：

\[
L_{box}=\frac{1}{4}\lVert b_i-\hat b_j\rVert_1
\]

## 4. 明显错误查询拒绝

标准匈牙利算法会强制匹配`min(Q,G)`对，即使所有查询都明显错误。为满足错误查询可保持无匹配的要求，I23增加`max_match_cost=4.0`：匈牙利求解后，只保留总代价不超过4.0的配对。

该门槛经过两类保护测试：

- 零logit、中性初始化查询且框正确时仍可匹配，避免训练初期正监督完全中断；
- 掩码与GT强烈相反且框错误时拒绝匹配，查询和GT均保持未匹配。

此门槛已写入独立配置，后续可进行敏感性消融；不得在同一正式实验中无记录地修改。

## 5. 单元测试

11/11项通过，覆盖：

1. 一个查询对应一个组件；
2. 三个重复查询对应一个组件时仅匹配一个；
3. 强错误查询无匹配；
4. 中性初始化查询仍可匹配；
5. 查询少于组件；
6. 查询多于组件；
7. 空GT；
8. 空查询；
9. padding查询和GT不进入匹配；
10. Dice、BCE和框代价矩阵尺寸及数值正确；
11. 查询索引与GT索引均满足一对一约束。

## 6. 真实组件目标验收

使用I20中的真实记录`EORSSD/train/0027`前三个组件构造测试：

- 查询0、1、2分别为三个正确组件预测；
- 查询3重复预测组件0，但质量较低；
- 查询4为与组件0强烈相反的错误预测。

验收结果：

| 项目 | 结果 |
|---|---|
| 匹配查询 | `[0,1,2]` |
| 匹配GT | `[0,1,2]` |
| `target_for_query` | `[0,1,2,-1,-1]` |
| 未匹配查询 | `[3,4]` |
| 未匹配GT | 空 |
| 匹配代价 | 0.02919、0.03108、0.03042 |
| 一对一约束 | 通过 |

附加场景中，一个查询面对三个组件时只匹配一个并保留两个未匹配GT；两个查询面对空GT时均返回`-1`。
